# 健康检查核验项目记录与后台队列

2026-11-12。本地服务能响应 HTTP，但历史结果不可读时，原健康接口仍返回 200。现在检查现有 SQLite 项目记录以及后台队列任务是否存活；任一失败，返回 HTTP 503 和 `status: degraded`。它用于识别服务故障，不是模型画质或 GPU 可用性的保证。

## 现场基线与恢复

在[48518c7](https://github.com/sakorman/web-scan/commit/48518c7)发现健康接口返回 200 / ok，而项目列表返回 500。服务日志显示 `sqlite3.OperationalError: unable to open database file`；同一目录的新进程可以读库，能够识别已安装的 PyTorch、PyCOLMAP 和样例。现有服务却报告运行库和样例不可用，尚未确定访问失效的根因。

确认没有排队或运行中的重建后，正常停止并重新启动本地服务。重启前后均有 19 个项目、321 张照片记录、52 个任务，历史接口恢复 200，数据库与后台队列检查均为 true。未改动系统权限或清理历史文件。此次重启恢复了可用性；健康检查修复只负责及时暴露同类失效，不能防止其再次发生，也不会自行重启训练。

## 实际改动

- 以 SQLite URI `mode=ro` 打开现有目录数据库，分别读取 sessions、frames、jobs 至多一条记录。缺库不创建空库，缺表或无法读取返回失败；每次连接都显式关闭。
- SQLite 锁等待超时为 250 毫秒，不沿用业务请求的 30 秒等待。普通 WAL 写事务仍允许只读检查，避免将正在入队的任务误判为服务故障。
- 健康接口增加 `database_available` 和 `worker_running`。启用队列时，未启动、已结束或已取消的后台任务不能报告正常；测试中显式关闭队列时后者为 null。
- 原版本信息和能力字段仍返回。成功为 HTTP 200 / ok，检查失败为 503 / degraded；响应不包含本地路径或底层异常文本。

50 次本地数据库探测的中位数为 0.085 ms，最大 0.252 ms，仅含只读探测，不含 HTTP、版本和样例检查，文件缓存未清空。锁超时不是整个健康请求的绝对时限。一次短查询也不能证明全库完整、磁盘可写、所有历史模型可下载，或后台队列没有卡住；后续监控仍需结合实际任务进度与错误记录。[现场状态、探测成本和新任务记录](benchmarks/service-readiness.json)

## 依据

[Viser 当前实现（viser-project，448ca33，Apache-2.0）](https://github.com/viser-project/viser/blob/448ca33ec61cec37876d29e48872dcd0ea112e5a/src/viser/infra/_infra.py#L460)在后台服务实际启动后再发出 ready 信号。这个相邻三维工具的做法提示应检查服务所依赖的后台状态，不能只看进程存在；本轮未复制其实现，也不把它当作 SQLite 检查的直接依据。

只读连接与缺库行为依据 [SQLite URI 官方说明](https://sqlite.org/uri.html)及 [Python sqlite3 文档](https://docs.python.org/3/library/sqlite3.html#how-to-work-with-sqlite-uris)。Ashim Dahal 等的近期[三维高斯系统综述（2026-10，v1）](https://arxiv.org/abs/2610.17513v1)区分渲染、构建与维护阶段；此次检验的是本地项目服务的可用性假设，不涉及论文模型的复现、CUDA 性能或视觉质量提升。

## 实拍队列回归

恢复后的 8787 服务通过实际 `POST /api/jobs` 队列串行完成 ETH3D pipes 和 office 两个新任务。输入均为纯 RGB，共享 RADIAL，相机来自本机 SfM 缓存，不使用官方位姿、深度或雷达。Brush 0.3.0 / Metal，种子 42，3,000 步，512 像素长边，15 万高斯上限；输入照片 1600×1067。留出照片参与 SfM，不参加高斯训练。训练期间每秒读取健康状态，pipes / office 分别 24 / 25 次全部正常。

| 场景 | 定位/输入；训练/留出 | 高斯 / PLY 字节 | SfM 缓存恢复 / 训练评估导出 / 总任务秒数 | 512×341 留出 PSNR / SSIM |
| --- | --- | ---: | ---: | ---: |
| pipes | 14/14；12/2 | 11,780 / 2,781,630 | 0.0304 / 23.9822 / 24.07 | 19.481394 dB / 0.78931653 |
| office | 26/26；22/4 | 14,408 / 3,401,838 | 0.0439 / 23.6298 / 23.74 | 21.932487 dB / 0.88952523 |

两组均无失败视角，读取完整 SH3、核对评测图摘要并验证 PLY HTTP Range 返回 206 与本地字节一致。时间不含照片准备和上传，不属于冷启动测速。office 本次服务缓存的内参与前几轮离线控制任务不同，因此不能将表中分数与那些任务直接作画质比较。这两次结果只验证恢复后的实际服务流程，没有新的画质对照、同视角截图或漫游结论；已知空洞、重影和细节限制仍见[现有记录](GMDEPTH-TARGETS.md)。没有在 GPU 训练时打开浏览器渲染。

10 项新增测试覆盖带特殊字符的目录、项目保留、目录及数据库文件缺失、三张表缺失、损坏文件、WAL 写事务、独占锁超时恢复和后台队列停止。294 项后端、18 项前端、类型检查与生产构建通过，仅保留既有 TestClient 弃用和查看器包体积提示。

## 使用与复现

```sh
curl --fail http://127.0.0.1:8787/api/health
.venv/bin/python -m pytest -q tests/test_health.py
```

异常测试只操作临时目录，不在真实项目目录移走数据库或修改权限。新任务配置、相机参数、模型摘要、实际任务编号与指标保存在[测量记录](benchmarks/service-readiness.json)；真实照片归属 Schöps 等的 ETH3D，许可 CC BY-NC-SA 4.0，见[第三方说明](../THIRD_PARTY_NOTICES.md)。原始照片、历史模型与运行日志留在本地。

后续若再次失效，先记录健康字段、任务状态与数据库访问错误，再区分进程运行环境、目录可访问性和队列异常；不要仅凭重启成功宣称根因已修复。
